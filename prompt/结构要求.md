# 任务：构建最简可用的「论文阅读与复现」Codex 工作流模板

你要在当前仓库中直接实现一个通用模板，不要只给方案。

## 一、最终目标

用 Codex 作为主模型/orchestrator，其他模型作为子模型辅助，搭建一套论文阅读、信息抽取、复现可行性分析和实验规划工作流。

使用者后续会补充具体研究方向、文献功能和复现细节。当前阶段只做：

1. 简单的模型配置体系。
2. 清晰、可检索、可追溯的项目文件结构。
3. 文献模块的功能骨架和扩展点。
4. 复现模块的功能骨架，包括线上代码/模拟与线下实验室路线的判断框架。
5. 最小可用的 CLI 和测试。

## 二、最简架构原则

必须遵守：

1. 顶层只允许 5 个目录：
   - `config/`
   - `workflow/`
   - `projects/`
   - `tools/`
   - `tests/`

2. 根目录只保留这些入口文件：
   - `AGENTS.md`
   - `README.md`
   - `ROADMAP.md`
   - `requirements.txt`
   - `.env.example`
   - `.gitignore`

3. 不创建 `docs/`、`src/`、`scripts/`、`prompts/`、`schemas/`、`templates/` 等顶层目录。

4. 一个概念只放一个地方：
   - 模型配置 → `config/`
   - 工作流说明、模块功能、prompts、schemas、templates → `workflow/`
   - 实际研究项目和数据 → `projects/`
   - CLI 与模型适配器 → `tools/`
   - 测试 → `tests/`

5. 单一事实源：
   - 每篇论文的 `meta.yaml` 是论文基础信息的唯一来源，不维护重复的全局 registry。
   - 每个复现 claim 的 `claim.yaml` 是 claim 的唯一来源。
   - 项目根目录 `INDEX.md` 由工具扫描生成。
   - 项目状态记录在 `project.yaml`，不再单独建 `state.yaml`。

6. 默认只设置 3 个子模型角色：
   - `literature-reader`
   - `reproduction-analyst`
   - `verifier`

   后续可以扩展角色，但不要默认铺开很多角色。

7. 默认技术栈：Python 3.11+，只依赖 `PyYAML`。不要引入 Web 框架、数据库、Docker、向量数据库、复杂调度系统。

8. 未明确的信息写 `TODO(user)`，集中记录在 `ROADMAP.md` 的待确认区，不要脑补。

- `bootstrap` 自动根据 `models.example.yaml` 生成 `models.local.yaml`，如果文件已存在则不要覆盖。
- 如果本机 Codex 支持原生 profile 或 subagent 配置，优先复用；具体方式写进 `workflow/README.md`，不要凭空编造配置字段。

## 五、主模型编排

根目录 `AGENTS.md` 必须规定 Codex 为本仓库的 orchestrator：

1. 开始工作先读：
   - `workflow/README.md`
   - `workflow/literature.md`
   - `workflow/reproduction.md`
   - 当前项目的 `project.yaml`
   - 当前项目的 `research-profile.yaml`
   - 当前项目的 `INDEX.md`

2. 工作流程：
   - 判断当前项目阶段。
   - 拆解任务。
   - 根据 `config/models.local.yaml` 的 `routing` 生成标准任务包。
   - 路由给对应子模型。
   - 汇总结果。
   - 验证来源。
   - 更新项目状态、索引和运行日志。

3. 子模型输出默认是草稿，重要结论必须由主模型核对来源后才能进入正式结果。

4. 必须严格区分：
   - 事实
   - 原文引用
   - 推断
   - 未知

5. 禁止编造论文内容、实验结果、代码运行结果或线下实验条件。

6. 外部调用、付费操作、删除文件、覆盖原始资料、耗时实验，必须先 dry-run 或请求确认。

7. 如果本机 Codex 支持原生 subagent，可以直接调度，但必须：
   - 使用统一角色名。
   - 生成标准任务包。
   - 将输入、输出、状态写入 `.runs/`。
   - 保证结论可追溯到来源。

8. 如果不支持原生 subagent，通过 `tools/wf.py run` 或 `manual` 适配器调度。

统一任务包格式见 `workflow/templates/task.yaml`：

```yaml
task_id: TODO
role: literature-reader
objective: TODO
inputs: []
allowed_paths: []
context: {}
output_schema: null
source_refs: []
```

## 六、项目模板

`projects/_template/` 是最小项目骨架：

```text
project.yaml
research-profile.yaml
INDEX.md
00_inbox/
10_literature/
  papers/
  matrix.md
20_reproduction/
  README.md
30_outputs/
```

项目内的文件规则：

- `00_inbox/`：临时资料、未归档链接、待处理 PDF。
- `10_literature/papers/<citekey>/`：一篇论文一个目录。
  - `meta.yaml`：元数据和状态。
  - `note.md`：阅读笔记。
  - `extraction.yaml`：结构化抽取。
  - `source/`：原始论文、补充材料、代码链接记录等。
- `10_literature/matrix.md`：跨论文对比矩阵，后续可由工具生成。
- `20_reproduction/<claim-id>/`：一个 claim 一个目录。
- `30_outputs/`：报告、图表、综述、最终输出。
- `INDEX.md`：由 `wf.py index` 生成，不要手工维护。
- `project.yaml`：记录项目标题、阶段、当前 claim、下一步动作。
- `.runs/`：隐藏运行日志目录，自动生成。

命名规范：

- 目录和文件使用 `kebab-case`。
- 论文使用稳定 `citekey`。
- 日期使用 `YYYY-MM-DD`。
- claim 目录建议使用 `<citekey>--<claim-slug>`。
- 原始资料只读，衍生结果单独存放，不能混在一起。
- 生成物必须记录：
  - `generated_by`
  - `model_role`
  - `prompt_version`
  - `source_refs`
  - `created_at`
  - `status`
- 所有结论必须能追溯到来源文件、页码、段落或代码位置。

## 七、文献模块

`workflow/literature.md` 写清楚功能地图和扩展点，但当前只实现骨架，不实现复杂算法。

功能地图包括：

- 入库：PDF、链接、BibTeX、手工录入。
- 元数据：标题、作者、年份、venue、DOI、代码链接、数据链接。
- 结构化抽取：claim、method、data、baselines、metrics、results、limitations、relevance。
- 综合：对比矩阵、主题地图、相关工作、矛盾点、研究空白、可复现性标签。
- 问答：基于本地语料回答问题，答案必须带引用。
- 状态：`unread`、`triage`、`read`、`extracted`、`synthesized`。

当前实现范围：

- 论文目录和模板。
- `meta.yaml`、`extraction.yaml`、`note.md` 的字段定义。
- `paper.schema.json`。
- `literature-reader` prompt。
- `matrix.md` 模板。
- 可以用占位数据演示的空流程。

后续再做：

- PDF 解析。
- 联网检索。
- 向量数据库。
- 自动生成完整综述。

不要假装已经实现这些后续功能。

## 八、复现模块

`workflow/reproduction.md` 写清楚功能地图和扩展点。

复现分析的核心输入：

- 论文或 claim。
- 项目 `research-profile.yaml`。

分析每个 claim 所需的：

- 代码
- 数据
- 算力
- 软件
- 设备
- 耗材
- 实验室环境
- 人员技能
- 时间
- 预算
- 伦理与合规

分类必须至少支持：

- `online-code`
- `online-simulation`
- `offline-lab`
- `hybrid`
- `observe-only`
- `unreproducible`

每个 claim 的输出放在 `20_reproduction/<claim-id>/`：

```text
claim.yaml
feasibility.md
plan.md
online/
lab/
results/
```

`claim.yaml` 至少记录：

- claim_id
- paper_citekey
- claim_text
- required_resources
- available_resources
- resource_gaps
- route
- confidence
- validation_criteria
- stop_conditions
- status

`feasibility.md` 至少包含：

- claim 原文和出处。
- 所需资源与现有资源匹配情况。
- 分类结果。
- 线上替代方案。
- 线下实验方案。
- 最小可行复现。
- 资源缺口和风险。
- 验证标准。
- 停止条件。

`plan.md` 至少包含：

- 选定的复现路线。
- 步骤和依赖。
- 数据与环境要求。
- 里程碑。
- 验证方法。

`online/` 用于代码复现和模拟：

- 环境配置。
- 代码结构。
- 数据准备。
- baseline。
- 指标。
- 复现步骤。

`lab/` 用于线下实验：

- 实验协议。
- 设备和耗材清单。
- 安全与伦理要求。
- 记录规范。
- 数据交接。

`results/` 存放结果、图表、日志和分析。

当前只实现：

- schema。
- 模板。
- prompt。
- 目录结构。
- 可行性分类的占位逻辑。
- mock 演示流程。

不要伪造运行结果，不要默认使用者拥有实验室条件。

## 九、tools/wf.py 与适配器

`tools/wf.py` 实现最小 CLI，所有路径相对于仓库根目录解析。

必须支持：

```bash
python tools/wf.py bootstrap
python tools/wf.py doctor [--offline]
python tools/wf.py init <slug> --title "..."
python tools/wf.py new paper <project> <citekey>
python tools/wf.py new claim <project> <citekey> <claim-slug>
python tools/wf.py index <project>
python tools/wf.py validate <project>
python tools/wf.py run <project> <task.yaml>
python tools/wf.py demo
```

行为要求：

- `bootstrap`：
  - 从 `models.example.yaml` 创建 `models.local.yaml`。
  - 从 `.env.example` 创建 `.env`，如果不存在。
  - 检查 `PyYAML`。
  - 最后提示下一步命令。
  - 不覆盖已有文件。

- `doctor`：
  - 检查目录结构。
  - 检查配置语法。
  - 检查环境变量是否存在。
  - 检查适配器是否可用。
  - 不打印密钥。
  - `--offline` 下绝不访问网络。

- `init`：
  - 从 `projects/_template/` 复制新项目。
  - 写入 `slug`、`title`、创建时间。
  - 不覆盖已有项目。

- `new paper`：
  - 从 `workflow/templates/paper/` 创建 `<citekey>/`。
  - 填入 `citekey` 和默认状态。

- `new claim`：
  - 从 `workflow/templates/claim/` 创建 `<citekey>--<claim-slug>/`。
  - 填入 `claim_id`、`paper_citekey` 等字段。

- `index`：
  - 扫描 `project.yaml`、`research-profile.yaml`。
  - 扫描 `papers/*/meta.yaml`。
  - 扫描 `20_reproduction/*/claim.yaml`。
  - 扫描 `30_outputs/`。
  - 生成项目根目录 `INDEX.md`。

- `validate`：
  - 检查项目结构和必要文件。
  - 检查 YAML 能否解析。
  - 检查关键字段。
  - 检查 route 是否合法。
  - 检查 `source_refs` 指向的文件是否存在。
  - 不强制引入 `jsonschema`，但 schemas 必须作为契约保留。

- `run`：
  - 读取任务包。
  - 根据 `role` 找到对应 prompt。
  - 创建 `.runs/<timestamp>-<task-id>/`。
  - 写入 `task.yaml`、`prompt.md`、`run.yaml`。
  - 通过对应 adapter 执行。
  - `manual`：只生成 prompt，等待人工把结果写入 `response.md`。
  - `mock`：返回占位结果。
  - `command`：执行配置中的外部命令。
  - `openai_compatible`：优先用标准库 `urllib.request` 实现 HTTP 调用，密钥从 `api_key_env` 读取。

- `demo`：
  - 使用临时目录运行完整空流程：
    `init → new paper → new claim → index → validate → run(mock)`。
  - 不污染 `projects/`。
  - 不需要真实 API key。

适配器统一放在 `tools/adapters.py`，接口保持稳定，具体厂商实现不得影响目录结构。
