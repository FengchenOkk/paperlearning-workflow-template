# 任务：优化现有工作流结构，使主模型、子模型、论文、概念、Zotero、知识图谱和复现模块之间的连接更高效、更紧密

## 零、总原则

当前仓库已有：

- 主模型 commander-reviewer
- 子模型 primary executor
- 论文编号目录：`meta.yaml`、`01_source/`、`02_translation/`、`03_reading/`、`04_analysis/`、`05_notes/`
- Zotero 联动
- 知识网络
- 通用复现扩展接口
- `.runs/` 任务和评审日志

本轮不新增顶层目录，不破坏已有功能。

优化目标：

1. 任何对象都有稳定 ID。
2. 任何连接都引用 ID，不直接依赖易变的文件路径。
3. 机器统一通过 `INDEX.json` 解析 ID。
4. 任务通过 `task-contracts.yaml` 定义输入、输出和验收标准。
5. 子模型只拿到完成任务所需的最小上下文。
6. 主模型只拿到评审所需的最小材料。
7. 所有产物、任务、链接、Zotero 元数据和知识图谱可以自动校验。
8. 重复运行稳定，不覆盖人工内容，不产生悬空引用。

## 一、统一 ID 体系

所有核心对象必须使用稳定 ID。

```text
project:<project-slug>
paper:<citekey>
concept:<concept-slug>
principle:<principle-slug>
formula:<citekey>:<formula-id>
claim:<citekey>:<claim-slug>
topic:<topic-slug>
task:<task-id>
attempt:<task-id>:<attempt-number>
artifact:<artifact-id>
```

要求：

- ID 一旦创建，不因为文件移动、重命名或重新同步而改变。
- Zotero item key 只用于映射，不替代 `paper:<citekey>`。
- 目录名和文件名可以变化，ID 不变。
- 所有引用优先使用 ID。

## 二、统一链接模型

所有核心文件都必须包含 `id` 和 `links`。

### 1. meta.yaml

```yaml
id: paper:<citekey>
type: paper
project_id: project:<project-slug>
zotero_key: TODO
links: []
```

### 2. analysis.yaml

```yaml
id: analysis:<citekey>
type: analysis
paper_id: paper:<citekey>
links: []
```

### 3. concept.md front matter

```yaml
id: concept:<concept-slug>
type: concept
paper_ids: []
links: []
```

### 4. claim.yaml

```yaml
id: claim:<citekey>:<claim-slug>
type: claim
paper_id: paper:<citekey>
formula_ids: []
concept_ids: []
links: []
```

### 5. 统一 link 格式

```yaml
links:
  - rel: uses
    target: concept:<concept-slug>
    evidence: []
    confidence: high
    status: verified
```

允许的 `rel` 至少包括：

```text
introduces
uses
extends
contrasts
prerequisite
similar-first-principle
similar-review
similar-concept-set
belongs-to-topic
supports-claim
derived-from
generated-from
```

要求：

- `links` 是关系的源数据。
- `knowledge-graph.json` 从 `links` 自动生成。
- 不允许在多个地方手工维护同一关系。
- 每个 link 必须有证据和置信度。
- 自动推断的 link 只能是 `candidate`。

## 三、机器索引 INDEX.json

项目根目录新增自动生成文件：

```text
projects/<project>/INDEX.json
```

它由 `wf.py index` 生成，是机器连接中心。

建议结构：

```json
{
  "schema_version": 1,
  "project_id": "project:TODO",
  "generated_at": "TODO",
  "artifacts": {
    "paper:TODO": {
      "type": "paper",
      "path": "10_literature/papers/TODO/meta.yaml",
      "anchors": [],
      "hash": "sha256:TODO",
      "updated_at": "TODO"
    }
  },
  "aliases": {
    "zotero:TODO": "paper:TODO"
  },
  "links": [],
  "tasks": {}
}
```

要求：

- `INDEX.json` 是 ID 到路径、锚点、哈希、任务状态的解析器。
- 所有任务、评审、图谱、Zotero 同步都通过它解析输入输出。
- `INDEX.json` 不保存正式结论，只保存连接信息。
- 输入文件变化后，哈希变化可被检测。
- `INDEX.json` 可完全删除并重新生成。
- `INDEX.md` 保留人类可读视图，`INDEX.json` 提供机器视图。

## 四、任务契约 task-contracts.yaml

新增：

```text
workflow/task-contracts.yaml
```

它定义任务类型、执行角色、输入、输出、验收标准和最大尝试次数。

```yaml
version: 1

tasks:
  literature-translate:
    role: literature-reader
    inputs:
      - type: paper.meta
      - type: paper.source.text
    outputs:
      - type: paper.translation
        path: "02_translation/translation.md"
        id_template: "translation:<citekey>"
    acceptance:
      - full_sections
      - terminology_consistency
      - source_refs
      - no_omissions
    max_attempts: 3

  literature-close-read:
    role: literature-reader
    inputs:
      - type: paper.meta
      - type: paper.translation
      - type: paper.source.text
    outputs:
      - type: paper.reading
        path: "03_reading/reading.md"
        id_template: "reading:<citekey>"
    acceptance:
      - required_sections
      - evidence_traceable
      - no_fabrication
    max_attempts: 3
```

要求：

- 任务必须由 contract 定义。
- 没有 contract，不允许派发。
- 没有验收标准，不允许派发。
- 输入输出必须是 artifact ref，不直接写随意路径。
- `config/models.example.yaml` 中的 routing 负责 task type 到 role 的映射。
- `task-contracts.yaml` 负责 task type 到输入输出和验收标准的映射。

## 五、ArtifactRef 统一格式

任务包、上下文包、评审包统一使用 ArtifactRef。

```yaml
artifact_ref:
  id: paper:TODO
  type: paper
  path: TODO
  anchor: null
  role: input
  required: true
  hash: TODO
```

要求：

- `path` 只是解析结果，不是连接主键。
- `id` 才是主键。
- `hash` 用于检测内容变化。
- `anchor` 用于定位 Markdown 章节。
- 任务输入输出全部使用 ArtifactRef。

## 六、上下文包

`wf.py task run` 执行前，必须先构建上下文包：

```text
.runs/<task-id>/context/
├── manifest.yaml
├── context.md
└── files/
```

`manifest.yaml`：

```yaml
task_id: TODO
task_type: literature-translate
role: literature-reader
contract: workflow/task-contracts.yaml#literature-translate
inputs:
  - id: paper:TODO
    path: TODO
    anchor: null
    hash: TODO
outputs_expected: []
acceptance_criteria: []
```

`context.md`：

- 只包含完成任务所需内容。
- 包括必要原文片段、已有术语、约束和输出模板。
- 不包括完整仓库扫描结果。
- 大文件只引用路径，不复制。
- 超过大小限制时截断并明确标记。

要求：

- 子模型只读上下文包，不自行全仓扫描。
- 上下文构建失败时不允许执行任务。
- 上下文包可复现、可审计、可缓存。
- 相同输入产生相同上下文包。

## 七、结果包

子模型每次执行写入：

```text
.runs/<task-id>/attempts/<attempt>/
├── prompt.md
├── response.md
├── result.yaml
├── artifact-index.yaml
└── self-check.md
```

`result.yaml`：

```yaml
task_id: TODO
attempt: 1
status: submitted

summary: TODO
created_artifacts: []
updated_artifacts: []
evidence: []
unresolved_issues: []
confidence: TODO
self_check: {}
```

`artifact-index.yaml`：

```yaml
artifacts:
  - id: translation:<citekey>
    type: translation
    path: 02_translation/translation.md
    anchors: []
    hash: TODO
```

要求：

- `created_artifacts` 和 `updated_artifacts` 必须能被 `INDEX.json` 解析。
- 不存在于 INDEX.json 的新产物必须登记。
- 产物路径变化后，任务接受时必须更新 INDEX.json。
- 子模型自检不能替代主模型评审。

## 八、评审包

主模型评审前，工具构建：

```text
.runs/<task-id>/reviews/<attempt>/
├── review-bundle.md
├── acceptance.yaml
├── evidence.yaml
└── links.yaml
```

`review-bundle.md` 只包含：

- 任务目标
- 验收标准
- 子模型摘要
- 产物路径
- 新增/修改的链接
- 证据索引
- 未解决问题
- verifier 报告摘要

主模型不默认读取整篇论文和全部上下文，只读评审包并按需抽查。

主模型评审输出：

```text
.runs/<task-id>/reviews/<attempt>.yaml
```

```yaml
task_id: TODO
attempt: 1
reviewer: main
decision: revise
# accept | revise | reject | block | escalate

passed_criteria: []
failed_criteria: []
issues: []
required_changes: []
evidence_checks: []
next_action: TODO
reason: TODO
```

要求：

- `accept` 必须所有验收标准通过。
- `revise` 必须列出可修复问题。
- `block` 用于缺资料、缺用户输入或达到最大尝试次数。
- 主模型意见必须映射到 `criterion`。
- 不接受纯主观理由造成的无限返修。

## 九、连接更紧密的任务闭环

完整闭环：

```text
用户目标
  -> 主模型拆解
  -> 生成 task contract 实例
  -> 构建 context bundle
  -> 子模型执行
  -> 生成 result bundle
  -> 构建 review bundle
  -> 主模型评审
  -> accept 或 revise
  -> 更新 INDEX.json
  -> 更新 knowledge-graph.json
  -> 更新 knowledge-map.md
  -> 更新项目 INDEX.md
```

要求：

- 每次状态变化都写 `.runs/<task-id>/status.yaml`。
- `INDEX.json` 必须反映任务状态。
- `knowledge-graph.json` 必须反映新链接。
- 主模型只能通过 `accept` 使正式产物生效。
- 返修包只传上轮问题和必要上下文，不重传全部输入。

## 十、Zotero 紧密连接

Zotero 同步使用统一 ID 和 INDEX.json：

- Zotero item key 映射到 `paper:<citekey>`。
- collection 映射到 `topic:<slug>`。
- tag 映射到 `topic:<slug>` 或 `concept:<slug>`。
- 附件路径写入 `01_source/` 和 `meta.yaml`。
- 同步时先查 `INDEX.json.aliases`，避免重复创建论文。
- 如果 citekey 发生变化，必须保留旧别名。
- 同步只更新元数据和链接，不覆盖人工内容。

`config/zotero.example.yaml` 的同步策略增加：

```yaml
sync:
  use_index_json: true
  preserve_aliases: true
  link_collections_to_topics: true
  link_tags_to_topics: true
  update_hash: true
  dry_run_default: true
```

## 十一、知识图谱紧密连接

`knowledge-graph.json` 不再依赖临时扫描，而是：

1. 读取 `INDEX.json` 解析 ID 到路径。
2. 读取所有 artifact 的 `links`。
3. 合并 Zotero topic 关系。
4. 生成节点、边、聚类和学习路径。
5. 写回 `knowledge-graph.json`。
6. 用 `INDEX.json` 校验所有边引用有效。

新增节点类型：

```text
paper
concept
principle
formula
claim
topic
task
artifact
```

要求：

- 每条边必须能解析到 INDEX.json 中的节点。
- 不允许出现悬空节点。
- 每条边必须有证据、权重、置信度、状态。
- 自动候选边不能直接升级为 verified。
- 主模型或 verifier 审核后才可升级。
- `knowledge-map.md` 从图谱生成，人工区域保留。

## 十二、复现模块紧密连接

`20_reproduction/<claim-id>/claim.yaml` 使用统一 ID：

```yaml
id: claim:<citekey>:<claim-slug>
type: claim
paper_id: paper:<citekey>
formula_ids: []
concept_ids: []
links: []
```

要求：

- 复现 claim 自动进入知识图谱。
- 私有复现扩展通过 `INDEX.json` 和 ArtifactRef 读取论文、公式、概念和 claim。
- 公共模板只定义连接契约，不实现专业复现逻辑。
- 私有仓库写入的结果仍走 result bundle 和主模型评审。
- 不同方向的复现扩展不能修改公共 ID 体系。

## 十四、CLI 更新

保留现有命令，新增或增强：

```bash
python tools/wf.py index <project> --json
python tools/wf.py context <project> <task-id>
python tools/wf.py task run <project> <task.yaml>
python tools/wf.py task status <project> [task-id]
python tools/wf.py task review <project> <task-id> --attempt <n>
python tools/wf.py task accept <project> <task-id> --attempt <n>
python tools/wf.py task revise <project> <task-id> --attempt <n> --review <file>
python tools/wf.py validate --links <project>
python tools/wf.py validate --contracts
```

行为：

- `index --json` 强制更新 `INDEX.json`。
- `context` 构建上下文包。
- `task run` 先检查 task contract，再构建 context。
- `task accept` 更新 INDEX.json 和图谱。
- `validate --links` 检查悬空引用、重复 ID、无效 target。
- `validate --contracts` 检查任务契约与 routing 是否一致。

## 十五、优化要求

### 1. 稳定性

- 所有写入原子化。
- 所有生成幂等。
- 哈希变化检测。
- 连接解析失败不能破坏原文件。
- 单个坏链接只报警告，不中断全仓扫描。

### 2. 兼容性

- 旧论文目录自动迁移到编号目录。
- 旧关系尽量转为 `links`。
- 旧字段保留兼容层。
- 无 API Key 时 manual 模式可用。
- 无 Zotero 时手工流程可用。

### 3. 准确性

- 无证据不连边。
- 无来源不生成正式结论。
- 自动连接只标记为 `candidate`。
- 人工或主模型确认后才标记 `verified`。
- 悬空引用必须报告。

### 4. 可重复使用性

- 生成文件带 `schema_version`、`generated_by`、`generated_from`、`generated_at`。
- 排序稳定。
- 输入变化后可重新生成。
- 私有复现扩展通过固定接口接入。
- 任务契约可复用、可扩展、可校验。

## 十六、测试

必须增加测试：

1. ID 生成稳定。
2. INDEX.json 正确解析 ID 到路径。
3. 悬空 link 能被发现。
4. 重复 ID 能被发现。
5. task contract 缺输入时拒绝执行。
6. context bundle 正确生成最小上下文。
7. result bundle 正确登记新产物。
8. review bundle 只包含必要评审材料。
9. 主模型 accept 后 INDEX.json 和图谱同步更新。
10. 返修不会重复传全部上下文。
11. Zotero 同步通过 zotero_key 映射到已有 paper ID。
12. knowledge-graph.json 中所有边都能解析。
13. 重复运行 index 结果稳定。
14. 人工内容不被覆盖。
15. `python -m unittest discover -s tests` 通过。

## 十七、验收标准

1. 顶层目录不变。
2. 每篇论文目录命名清晰：
   `meta.yaml`、`01_source/`、`02_translation/`、`03_reading/`、`04_analysis/`、`05_notes/`。
3. 所有核心对象使用统一 ID。
4. 所有核心关系使用 `links`。
5. 项目根有 `INDEX.md` 和 `INDEX.json`。
6. 任务通过 `workflow/task-contracts.yaml` 定义。
7. 子模型只接收 context bundle。
8. 主模型只接收 review bundle。
9. 任务闭环能自动更新索引、图谱和状态。
10. Zotero、知识图谱、复现模块都通过 ID 和 INDEX.json 连接。
11. 所有自动连接可追溯、可验证、可重新生成。
12. 最终输出：
    - 修改摘要
    - 新目录树
    - ID 体系说明
    - 连接模型说明
    - 任务契约说明
    - CLI 说明
    - 测试结果
    - 最多 10 条待确认问题

先检查仓库，再增量实现。不要新增顶层目录，不要破坏已有功能，不要提交真实密钥和私密数据。
